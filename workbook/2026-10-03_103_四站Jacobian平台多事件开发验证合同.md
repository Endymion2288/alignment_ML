# Workbook 103 — 四站 Jacobian 平台多事件开发验证合同

## 0. 状态与授权边界

本文件是 WB102 封存后的**前瞻性开发合同**，不是结果报告。它记录下一阶段唯一允许的科学问题、事件选择、冻结控制、判据和失败回退。当前只创建合同；没有生成新物理输出、没有修改 solver/SE(3)/convergence/production backend、没有提交 Condor，也没有打开 held-out 或 sealed 数据。

证据：WB102 的封存清单为 `docs/wb102_jacobian_scale_result_manifest.json`，其中 `execution_contract=PASS`、`recovery_execution=PASS`、`hypothesis=SUPPORTED_BUT_LIMITED`，但 `qualification/physics_screening/final_oracle=NOT_EVALUATED`。WB102 工作簿第12节将“同一冻结算法和阈值的 seen 多事件开发验证”列为唯一下一路线。

**本合同的唯一问题：** WB102 在一个 seen、dummy-q/p、无 covariance/material 的 pilot 上观察到的五维 Jacobian plateau，能否在预先固定的多源多事件集合上重复出现？

这个问题只检验数值平台对 event/source/navigation 状态的稳定性。即使通过，也不能推出物理 common-track validity、association、detector precision、rank/identifiability、alignment qualification 或 ML readiness。

## 3. Frozen scientific algorithm

The implementation must reuse the WB102 source and decision code byte-for-byte wherever the code is independent of event indexing. Only event-loop plumbing, per-event output names, and aggregation may be added in a new isolated component. The following remain frozen:

- `lambda=(1.0,0.5,0.25,0.125)` and plateau `.5/.25/.125`;
- arms `disabled=0`, `tau=1e-8`, candidates `1e-9` and `1e-10`;
- caps `(10,0.1,0.01,0.001) m` and all three WB102 targets;
- nominal plus five-coordinate and alternating mixed perturbations, with central `+/-`, full and half amplitudes;
- five-dimensional state order, seed steps, output scales, `J`/`K` definitions and mixed closure formula;
- double reference ladder and the float ladder as sensitivity control;
- Jacobian budget `1e-6 + 0.001*abs(K_reference_fine)`, reference fraction `0.1`, uncertainty factor `10`, and all WB102 acceptance inequalities;
- dummy `q/p=+1e-5 MeV^-1`, no covariance, no material interactions, and no truth/association substitution;
- the actual FASER field service, geometry/conditions payload, ACTS mode, and isolated library identity used by WB102;
- no global alignment solve, local nuisance fit, prior/rank policy, SE(3) update, convergence policy or production backend change.

The event fixture supplies the xAOD path and ordinal. The actual EventInfo run/event header must be checked against the table before any result is accepted. The `(source path, ordinal, actual run, actual event)` tuple is the identity key; run/event alone is insufficient because the repository documents cross-source header collisions.

## 4. Per-event execution contract

Each of the six events must independently produce the complete WB102 matrix. No event may borrow another event's reference ladder, trial stream, field query, geometry object, or summary. Output directories must be disjoint and created with exclusive semantics.

For each event, the worker must preserve:

1. a fixture copy and raw-file identity manifest;
2. actual source/ordinal/header and geometry/conditions identity;
3. all four lambda outputs, all four arms, all caps, all targets and all mixed/coordinate perturbations;
4. complete trial and trace streams sufficient for the existing independent audit;
5. double and float reference ladders, node payload hashes, generated source/binary/library hashes and the worker exit receipt;
6. independent NumPy/scalar recomputation using the existing WB102 audit functions.

The expected matrix is 6 times WB102: `6*5056=30336` physical diagnostic calls and `6*600=3600` reference integrations, before controls. This is a long-running batch task. If implementation is later authorized, it must run through Condor after queue/slot inspection, with a new exclusive output root and no automatic retry. No Condor submission is part of this workbook.

## 5. Controls and negative controls

Every event retains the WB102 disabled and `tau=1e-8` controls; their outcome is reported descriptively and is not silently removed when they fail. The following controls are mandatory before a scientific verdict:

- wrong q/p unit and wrong sign controls are detected;
- zero/constant field and NaN/shape controls are rejected;
- changed source, ordinal, header, geometry, node, mesh, IOV, or sqlite identity is rejected;
- a missing lambda, cap, target, perturbation arm, trial stream, or reference ladder is rejected;
- an intentionally changed event identity cannot be merged into another event;
- one-column or one-cap corruption produces a non-PASS candidate decision;
- scalar summary and vectorized summary agree within the existing WB102 audit tolerance;
- repeated identical calls remain deterministic and no event's cache is reused across event boundaries.

These are execution and integrity controls. They are not evidence of detector physics or statistical qualification.

## 6. Prospective decision rule

### 6.1 Event-level rule

Run the existing WB102 `analyze` decision without changing constants. For each event:

- `PASS` means execution/identity/trial/scalar/reference gates pass and **both** candidate arms pass the complete frozen conjunction over plateau lambdas, four caps, three targets, all five Jacobian columns and mixed closure;
- `NOT_SUPPORTED` means the prerequisites are valid but any required candidate element, scale-consistency check or mixed closure fails;
- `UNKNOWN` means any required event identity, reference prerequisite, trial completeness, scalar audit, source/library hash, or execution gate is missing or invalid;
- infrastructure `FAIL` is recorded separately when the worker/reporting process fails, preserving all saved artifacts. A recovery may use a new exclusive directory, but cannot convert the original worker receipt into PASS.

The candidate arms, disabled arm, and weak arm are never selected after inspecting event outcomes. No threshold, lambda, cap, target, or event may be removed to obtain a PASS.

### 6.2 Corpus-level rule

The prospective corpus claim is `SUPPORTED_BUT_LIMITED` only if all six event-level results are `PASS`, all six have complete reference prerequisites, and all six pass independent trial/scalar audits. Any valid candidate failure yields `NOT_SUPPORTED` for this development hypothesis. Any missing/invalid prerequisite yields `UNKNOWN`; it is not counted as a scientific failure. A worker infrastructure failure remains a separate execution `FAIL` and requires an isolated recovery before interpreting available science.

The corpus report must include the complete event-by-event table, maximum and median decision ratios, the worst event/source, reference and mixed-closure diagnostics, and the exact number of tested versus expected cells. Pooled medians or averages are descriptive only and cannot hide a failing event.

## 7. What a result would establish

If the corpus passes, the evidence supports only this bounded statement: under the WB102 dummy-q/p, no-material, no-covariance numerical setup and the six preselected seen events, the frozen finite-difference platform reproduced its reference-consistent plateau. It would justify designing a larger seen development validation with an independently frozen event list.

If the corpus fails, the next stage is a single mechanism study chosen from the failing event/source and the preserved traces (for example event dependence, navigation branch, or reference mismatch). The response is not to tighten `tau`, delete a weak arm, omit a cap, select passing events, or begin ML/qualification.

Neither result authorizes physical qualification, reuse as an independent held-out test, opening sealed data, changing association, fitting global alignment, or training ML.
